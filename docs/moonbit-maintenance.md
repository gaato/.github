# MoonBit の上流変更を取り込む

目的は、自分のライブラリとアプリを上流の改善に合わせて良くすること。
依存の版を定期的に上げるだけの PR を作る運用にはしない。

## 調べる対象

- compiler / core / moon / moonrun と、利用中の async・x・外部ライブラリ。
- 自分の公開モジュール、利用アプリ、runner、サイト、Docker、devcontainer、共有 CI と health。
- archived repo、上流 fork、実験用 worktree は対象外。ただし比較の参照としては読む。

各回の記録には、調べた revision と配布バイナリの実際の版を残す。
main に入った機能と配布済みの機能は一致しないことがあるため、リリースノートだけで
採用を決めず、小さく実行して確認する。

## 一回の進め方

1. 作業中の変更と VCS を確認し、隔離が必要な repo は作業場所を明記する。
   既存の実装作業と保守変更を混ぜると、回帰の原因とレビュー対象が分からなくなるため。
2. 上流の差分を実装・テスト・呼び出し元と照らし合わせる。
   各候補に「自分のどのコードが良くなるか」「移行費用」「検証方法」を書く。
   API の意味を変える場合は、先に既存の契約と意図を確認する。
3. 改善は大きさで制限せず、価値と費用で判断する。
   単なる置き換えより、不要になった独自処理の削除や構成の変更が適切な場合もある。
   採用しなかった候補も、理由と再確認の条件を記録する。
4. compiler・core・runner を組として固定し、実際に使う backend と実行環境で検証する。
   バージョン文字列や依存解決の成功だけでは、実行互換性や性能を確認できないため。
5. リリース準備で依存を再解決し、公開モジュールと利用アプリを下流へ順に確認する。
   workspace のローカル版と registry の公開版を区別し、実際の解決結果を残す。
6. 公開する差分・検証結果・残る制約・リリース順序を提示する。
   push、PR、tag、パッケージ公開、デプロイは、その具体的な対象への承認後に行う。
   公開された履歴や通知は、後から取り消しても既に参照されている可能性があるため。

## 検証の見方

通常の repo gates に加え、変更に応じて以下を確認する。

| 対象 | 確認すること |
|---|---|
| MoonBit モジュール | fmt / check / test / info、公開 API 差分、README の実行例、docs audit |
| 非同期処理 | 中断、完了、資源の寿命、異常終了。成功ケースだけではリークや順序を検証できない |
| codecs | 全 backend、証明と負の対照、coverage ledger、参照実装との cross-check、必要な性能比較 |
| runner | 同じ Wasm を本家と実行して stdout / stderr / exit を比較。compiler・core・上流 pin ごとに参照キャッシュを分ける |
| アプリ・サイト | 更新したローカル成果物との組み合わせ、本番相当ビルドとローカル smoke |
| Docker / devcontainer | 実際の固定イメージ内で導入と実行。イメージ取得だけを動作確認とは数えない |
| CI / health | 通常 CI と canary のセットアップ・検証入口を揃え、失敗を変更ファイルとの関係で分類する |

既知の差は、意味と根拠を説明し、該当するテストだけを厳密に記録する。
テストの除外や広い出力の正規化で成功に見せないため。未解決の差が残る場合は
`UNSTABLE` とし、既存の問題・今回の回帰・環境制約を分ける。

## 記録

各回の評価は `docs/reviews/YYYY-MM-DD.md` に置く。
対象 repo、採用・保留した上流変更、解決した依存、実施した検証、未検証の範囲、
リリース候補を残すことで、次回は既に判断済みの範囲を読み直さず差分から始められる。
